## Summary

The show "Observability and AI explained - Grafana Labs" was published on July 31, 2026, featuring Senior Developer Advocate Nicole van der Hoeven. The discussion focused on the integration of AI within Grafana's observability tools, including Grafana Assistant, Grafana MCP, and k6, highlighting their roles in enhancing software development and incident management. Key takeaways included the importance of AI in alleviating the burdens of observability, the dual role of AI in observing systems and being observed, and the introduction of tools like investigations and agent observability for better incident response and AI evaluation. The session emphasized that AI is not meant to replace engineers but to empower them by automating tedious tasks and improving team collaboration.

Topics: Observability, AI, Grafana Assistant, Grafana MCP, k6, incident management, agent observability.

**Grafana Assistant** is an AI agent built into Grafana. It knows your telemetry, your dashboards, and your alerts. It's not just a chatbot; it doesn't just answer questions. It does the work, writes your queries, builds your dashboards, and creates deep reports about what it's found. The chances are pretty high that you can ask Assistant to analyze your data so that you don't have to.

Once you've decided what to build, AI can help you build it faster. But can it do it without you feeling like you've completely lost control? We have tools that make sure that you can observe your code every step of the way. For example, if you want to instrument your code, then you probably want to do so by reusing the same data sources, labels, and metrics that already exist in your stack. After instrumentation, if you want to debug while you're developing, you can query that same telemetry to see if the new metrics are actually flowing in. You can also use that information to troubleshoot performance issues for endpoints that you create. 

To help you build stuff, here are some of the tools that we've built that you can use. Assistant from within the Grafana UI lets you add tools to do things like create fixes and raise PRs on GitHub on your behalf, and that can even be triggered from Slack. 

But there are a few other tools in case you are already working with a coding agent and just want to be able to interface with Grafana resources. **GCX** is an open-source structured CLI for Grafana. It doesn't have a model of its own and instead allows your coding agent, like Claude Code or Cursor or Codex, whatever you're using, to interface with Grafana. GCX works across Grafana products, so you can use it to create alerts, query all the telemetry signals, create load tests, and more. GCX also lets you do everything that you can do with Assistant on your terminal. Note that the Assistant part is still not open source; you just have the option within GCX to link to Assistant. 

Sometimes you're using an agent that can't use a CLI like GCX. Maybe you're using a chat app like the Claude desktop app or ChatGPT. If it allows for MCP connectors, then you can use **Grafana MCP**. This gives you access to your Grafana stack. Grafana MCP is kind of like a standard protocol layer for interacting with Grafana resources, and it comes in two flavors. There's an open-source server that works with self-hosted Grafana and Grafana Cloud, but you run and maintain it yourself. Then there's Grafana MCP on Grafana Cloud. We host it, and you just get to use it without the maintenance burden. 

Now, stay with me. We also have three specialized MCP servers: one for Loki, one for Tempo (now built into Tempo itself), and one for k6. These MCP servers have some skills that are specific to each tool.

Aside from Grafana specifics, Smart it also tends to be more token efficient than third-party options. If your agent doesn't have shell access, then use Grafana MCP. Now, if you're building your own agent, then we also have an **AI SDK**. It's an open-source framework for building agents in Go. You can actually use it to build any agent, but it works especially well with all things Grafana, including built-in instrumentation and integration with something we call agent observability, which you'll hear about in just a second. This is also what we use internally to build some of the tools used in this video. 

We always want to do our best to prepare for the things that we can expect, but you know, in production, sometimes things happen that are completely unexpected. For that, there's **Investigations**. Investigations is like an agentic mode for Assistant that helps you triage issues. It can analyze telemetry, produce structured reports with hypotheses for incidents, and if you're using Grafana Incident Response Management on Grafana Cloud, you can also use Investigations to automatically kick off an investigation when an incident is declared. 

So, IRM handles the alerting, on-call, and incident workflow, and Investigations is the AI analysis layer that can plug into it. Investigations really gives you some context on why an incident is happening, and you can even enlist the aid of a swarm of multiple powerful agents to help you get to the bottom of things. It can also be good for helping you figure out what to do in case you're on call and handling an issue that you've never dealt with before. 

So, that's if you're already in the middle of a full-blown incident, but there are also things that you can do to stay ahead. Assistant has a feature called **Automations** that lets you save an Assistant prompt to be run either manually or on a recurring schedule. You can use this to do things in the background like creating daily summaries, deployment or latency reviews, and other routine repetitive tasks so that you can catch things before they actually happen. 

Also in Assistant is a watcher agent that you can use alongside static alerts. You can think of this as a sort of...

dynamic alert in that you describe what you care about, so it's based on your intent. Then it generates the telemetry tracks, you review them, and it watches those, letting you know when something looks suspicious. 

I also want to mention some machine learning features here that are part of the Grafana ML machine learning plugin. Don't confuse investigations with Sift investigations. I know, sorry about that. Sift is an ML feature specific to Kubernetes; however, it's no longer being actively maintained. The ML plugin also has two features that are still actively maintained: 

- **Grafana metrics forecasting**, which lets you predict the future behavior of a Prometheus series or other time series data source, and optionally alert on it.
- **Grafana outlier detection**, which identifies data points in a given series that are behaving differently from the rest.

Both are still useful for helping you forecast and spot issues before they happen, helping you breathe easier when you're tasked with maintaining and operating your apps and platform. 

Another use for ML in Grafana that's not within the plugin is called **adaptive telemetry**. It's an ML-driven cost reduction tool across the four main telemetry signals: metrics, logs, traces, and profiles. Each has its own adaptive sort of product. To help you react to incidents quickly, there's investigations to help you prevent them and be more efficient. You can use Assistant, metrics forecasting, outlier detection, and adaptive telemetry.

First, we have a testing and reliability tool called **k6** already. It can run browser-level and protocol-level tests, and now it comes with a lot of AI features to help you use it. On the OSS side, k6 comes with a built-in k6 MCP server that I mentioned earlier, and a command to bootstrap your coding agents with k6 skills, including the conversion of Playwright scripts to k6 scripts using those agents. 

On Grafana Cloud, the Assistant has a k6 script authoring mode for writing load tests so that you can run simple tests quickly or get a huge head start in writing more complex ones. It comes with all the best practices that you might not know of, like that you should add thresholds or tags and URL grouping, and so much more. So far in this video, we've mostly talked about using AI for observability. Now, let's go the other direction and talk a little bit about observing your AI. Testing AI is often called evaluation, but it's really the same discipline with the same purpose of proving that you can rely on something before you trust it. **Agent observability** is the way to observe your AI agents. We had this issue as well, and we decided to create an open-source benchmark for AI agents doing observability-specific workflows, and we call it **Olliebench**.
