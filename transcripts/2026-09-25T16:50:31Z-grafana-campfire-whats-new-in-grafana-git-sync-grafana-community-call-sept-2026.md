In summary, over the last 12 months, we have made significant improvements to Git Sync. We added support for any Git provider and implemented various authentication methods, including GitHub apps. We are also close to completing features like verified commits and user attribute commits. This means that when you commit from the Grafana UI, the person making the change will be attributed to the commit.

We have introduced different ways to organize folders and set up permissions, including the pull request flow, which has been revamped for ease of use. Feedback from the community on these changes is highly appreciated, as we aim to create the smoothest experience possible.

Another notable feature is the markdown support. When you sync the repository, you can see the markdowns and use them to govern and organize your dashboards, providing operational context directly in Grafana.

Looking ahead, we are focusing on several key areas based on community requests. One major request is to synchronize more resources within the same instances and repositories, which requires improvements in scalability and performance. Additionally, users have been asking for a built-in migration tool to help migrate existing resources more easily. Currently, this can be done with the GCX tool, but the process can be clunky and time-consuming, depending on how resources were set up.

The most requested resource type for Git Sync is alerts, which is one of the top requests in the Grafana community. Following that, library panels are also in high demand, as many users are synchronizing dashboards that include library panels.

We also discussed the integration of Git Sync with generated dashboards. The Foundation SDK allows users to generate dashboards from code, which can then be deployed and served by Git Sync. We aim to maintain parity between what users see in the repository and in Grafana, ensuring a consistent mental model.

In terms of future plugins, we want to ensure that any configurations or resources created by community plugins are also synchronized with Git. This will enhance the overall functionality and usability of Grafana.

Lastly, we addressed initial performance problems related to Git synchronization. We have implemented solutions to make the process more efficient, allowing for a smoother experience across various platforms and setups.

To tackle the question of what to do with the repository, where to store it, and how to secure it, we created a library in the Grafana community called Nano Kit. This library communicates through HTTP to the Git server, which is why we offer universal support for any Git provider. It retrieves only the necessary bits for synchronization or any other operations we want to perform. For instance, if we need to read one file, we can do so without having to clone the entire repository or know all the branches. We essentially cherry-pick what we need.

We observed significant improvements in polling, especially when running in the cloud. The process is very fast, and there is potential for further enhancements to reduce unnecessary API calls during synchronization. We chose not to store the content of the repositories for security reasons; we simply display the required information in Grafana and then forget it.

However, this read-only approach raises the question: do we perform actions on the Git repository using this library as well? Yes, we can write commits in a similar manner. With this library, we can determine the optimal size of a commit, decide how many files to include, and control how often we want to push changes. For example, if we need to import history, we can create one commit per version of the resource, allowing for a granular approach. Some bulk operations can be performed, which is where it gets interesting. For certain operations, it is approximately 300 times faster than calling and cloning repositories.
