## Multi-Tenant Query Support

Next, we have **multi-tenant query support**. I feel like basically everyone in this call got something in here. Multi-tenant queries were in our Jet product for a while, and we just never had space to get it over into open source. **Sage** took some time this past quarter to sneak that in, so Tempo OSS now supports full multi-tenant queries, which mirrors the capabilities of open-source Mimir and Loki. 

This may not be a feature that tons of people are interested in, but it’s definitely a killer feature for those running big multi-tenant cells who want to push streams of smaller data to different tenants. Humorously, it’s one of the most upvoted requests on our public Tempo repo. I do not know why, but people wanted it. Thanks to **SJ** for spending the time to get that one over there.

### Default Settings and Performance Improvements

**DePar 3** will be the default in 2.4; it was not the default in 2.3. Along with some TraceQL performance improvements, if you read through the changelog, you’ll see three or four TraceQL improvement-style PRs. You should see very strong improvements in performance with TraceQL. 

In addition, the dedicated columns we talked about in the last blog post with 2.3 should also contribute to strong performance in your TraceQL queries. If you’re not seeing improvements, it’s a good idea to file an issue in the repo or ask in Slack about the issues you’re experiencing, and we can help you get your cluster where it needs to be.

In terms of performance, we’ve added a **multi-level cache**. The caching story was always pretty weak in Tempo. We cached footers and Bloom filters, but footers were broken, and Bloom filters were the only thing that worked correctly with caching. With this rewrite, we now have a full tiered cache that supports frontend jobs. If people add queries to dashboards that execute repeatedly every 30 seconds or so on a dashboard refresh, that will be cached in the frontend. 

There is page-level caching in the queriers, which is similar to chunk caching on Loki. Bloom caching continues to work, and footer caching has been fixed. The caching story in Tempo has gotten quite a bit better. Check out that PR; we’ll definitely include details about this in the blog post on how to configure it. I hope it’s straightforward. We added a new config block where you can have all your caching configuration in one spot, and we’ll talk about some best practices there in the blog post.

We’ve seen some performance improvements across the board. SJ rolled that out to all of our Cloud clusters, and we saw what would you say, SJ? Like half the latency? 

**SJ:** "Yeah, B90 was pretty much half. That’s a little skewed; I won’t go into details."

No worries! The multi-level cache is a nice maturity improvement for Tempo in terms of your ability to operate it. It gives you the option to spend more money to make it faster, which is a nice option on the table now.

**Zack:** "Did you want to add anything about the page caching?"

**Marty:** "Yeah, I wanted to talk about the page caching a little bit more. I think that’s really the most powerful part of this. There’s the concept of the store gateway in some of Mimir or Loki, where it acts as a buffer between it and object storage. The page caching we’ve added is really our layer for that."

It's the raw IO that would normally come out of object storage that will now come out of MEC or Redis. I think that's like the really powerful part of this. As Joe was saying, you can really scale that up a lot, so it's however much IO you would like to buffer. If you have repeated queries or things like that that you really want to get performance on, the ceiling is way higher now with this caching than it was before. It's pretty cool—hundreds of gigs of caching or whatever you need.

We saw definite improvement on the page-level caching. As Mario mentioned, it's at that raw IO level. If you write a query and then adjust a single parameter, you're going to cache most of those pages on the second pass through, and you should see better performance on that second query. Trace by ID also saw really nice performance improvements with this page-level caching because it's hitting the same parts of the same blocks over and over again. Repeatedly asking for that same trace was a really nice performance improvement as well. 

With the page-level caching, it does have to be pretty big because it caches a lot; it takes a lot of volume. However, we've seen noticeable improvement in both search and Trace by ID.

I'd really like to hear about using this with on-prem object storage compatible products. Cloud vendors' object storage usually has a lot of headroom there—pretty high bandwidth and call rates—whereas on-prem you're more constrained for resources. I think this would be a great place for on-prem installations too.

This link you sent, the MCD link, is this what was done in Loki? The external store, is that the same thing as its NVMe caching? 

Yes, internally, Loki rolled out massive caching using this technology, basically in MCD, to lower their costs because now it's no longer in memory. It's not quite as fast as memory, but it is fast enough and it is quite good. Danny gave a talk about it—very cool!

This page-level caching could be a direction we go internally. Obviously, you can do it externally, but we might move to massive NVMe stock cache for our pages in our cloud products.

What else do we have here? Polling reduction—Zach did some great work on the polling, which will massively reduce the calls to the storage backend. Previously, on the polling cycle, we would pull what's called the tenant index. Every time we built the tenant index, we had to ask for every block individually, pulling details about every block to build what we call a tenant index, which then the other components would download. 

Now, blocks are immutable; they never change. This improvement is basically using an in-memory representation if it exists. Instead of asking for that same block over and over again, which was unnecessary, we see we already have that block in memory. We know it can't change; it's immutable, and we will not make that call. We've seen massive backend reduction in calls to the backend due to this polling change. This has been a real nice TCO improvement, as well as just kind of reducing that. Honestly, between the caching, if you set it up, and this polling improvement, which will just happen automatically, you should see Tempo overall just kind of tax your object storage less, and it should lower TCO quite a bit.
