The eBPF profiler provides insights into everything happening on a node. You can filter down later to what you really care about, but it gives you a good baseline understanding. If you need more runtime detailed information, eBPF can't necessarily access the runtime easily. Currently, the eBPF profiler focuses on events that we've seen, with CPU being the main resource that can be easily accessed from within the kernel.

For everything else, you either need to hope that your runtime supports profiles natively—Go is a very good example—or you need some form of SDK that provides that information and services it to you. Sometimes, you might not have control over the entire node where you run your application. There's a concept called USDT (User Statically Defined Tracers), which is a trace point that you keep visible to eBPF. This allows you to attach to a specific point in your program and inform potential future eBPF profilers where the memory information statistics are located. Theoretically, you can do this, but it is very hard to implement for every application out there. Essentially, some form of the allocator of the runtime will keep statistics and expose them to the eBPF profiler. This is the rough plan for memory profiling through eBPF.

You can gain a good understanding across all the languages installed on your host. If we go back to the initial picture, your application will need to provide more information. It will take time to integrate with all the potential allocators that need to keep statistics and expose them through the USDT trace point.

Regarding OpenTelemetry, they have separate collectors for metrics, logs, traces, and profiling. The reason for this separation is partly due to security concerns with eBPF. In contrast, Grafana Alloy does not have this issue, and everything can be integrated within Alloy. 

The deployment models differ. Alloy can function as both a metrics and profiling collector, while the OpenTelemetry collector aims to minimize how much runs in privileged mode. With Alloy, the configuration determines how much runs in that privileged mode. Essentially, it's the same binary, but you wouldn't necessarily run everything within one binary. For example, you might have a Helm chart that runs a privileged daemon set for profiling and a separate deployment for metric collection.

There are slight differences between the Alloy and OpenTelemetry collectors. Currently, the OpenTelemetry collector and the eBPF code are almost identical, with only a few bytes differing. However, Alloy allows you to selectively choose which applications to profile, which the OpenTelemetry eBPF profiler did not prioritize. We have a small patch to enable this feature in Alloy.
