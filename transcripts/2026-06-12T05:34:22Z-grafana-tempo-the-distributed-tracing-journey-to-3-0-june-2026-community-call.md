This essentially means that we are making three copies of the same data, and the reason for that is high availability. If one ingester is down, there is no problem because you have two other copies. **Grafana Tempo: The Distributed Tracing Journey to 3.0 (June 2026 Community Call)**

In this community call, we discussed how we rolled out Grafana Tempo in Grafana Cloud. We tried to be very careful and systematic in our approach, using a phased rollout. We started with phase one, then moved to phase two, and finally to phase three. For every phase, we took the time to gather metrics and ensure that everything was working perfectly before moving on to the next phase. We refer to this as a validation-driven transition. Essentially, there are success criteria, and we do not proceed to the next phase until the current one has been validated.

We utilized Vulture, our Tempo consistency tool, to validate that everything was functioning correctly, including queries, recent data, backend queries, metrics, and so on. This is a simplification of the entire rollout process. 

The first stage of phase one involved introducing Kafka. We added a Kafka producer in the distributor, which continued to write to the ingester and the metrics generator, but also began writing into Kafka. We determined the number of partitions and started pushing data into Kafka. 

The next phase involved adding the Kafka consumer, which included the block builder—the component responsible for creating blocks—and the metrics generator. Now, the metrics generator was receiving data from the distributor via gRPC while simultaneously receiving data from Kafka as a regular Kafka consumer. Once we validated that everything was functioning correctly, we stopped flushing blocks from the ingester. This step is not shown in the slide, but once we confirmed that the block builder was creating blocks correctly, we ceased flushing from the ingester, which then became a read path component.

The final phase involved adding the live store, which is another consumer from Kafka. The live store replaced the ingester, allowing us to remove the ingester from the equation, and now everything operates as a Kafka consumer. 

**Timeline of the Rollout**

Jav asked about the timeline for this phased rollout. It took us nearly a year to complete the migration for all the Tempo clusters around the world. We did not wait for all components to be finished; instead, we started deploying them one by one. As soon as we had something close to production with the block builder, we began deploying it in different clusters and then moved on to the next component.

**Migration to Tempo 3.0**

This is the last slide I have, which outlines how you, as a Tempo user in the open-source space, should approach migrating to Tempo 3.0. We discussed internally what the best way to do this would be and decided that the optimal approach is to spin up two clusters. You would run your Tempo 2.10 cluster as you currently do and then create a new cluster that uses the same object storage bucket. 

The idea is to perform the rollout incrementally using weighted routing. Start by moving 10% of your traffic from your old cluster to your new cluster and validate that everything is functioning correctly. We have a detailed migration guide available, which you can find in the links shared on the screen. 

This approach has worked well in the past for other internal migrations in Grafana, although not specifically for Tempo 3.0. It is crucial to disable compaction during the overlap period. While you are running your old compactor, you do not want to run the new backend scheduler and backend workers simultaneously, as this could lead to compacting blocks twice, which is risky. 

You should disable compaction in your new Tempo 3.0 cluster and scale down your old compactors while scaling up your Python workers in the new cluster. We have also created a new CLI tool, specifically the migrate command in the Tempo CLI, which helps you convert your old YAML into the new format, as some entries like ingesters and compactors are no longer valid.

We recommend using Vulture to run and point to the new cluster, allowing you to ingest traces and perform queries. This is likely the best validation tool you can use, but you should also conduct your own tests manually or have your dashboards ready.
