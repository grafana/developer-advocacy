### 4.2 Release Highlights

In the 4.2 release, we introduced a ton of new features. In the telemetry services section of the Helm chart, where you can deploy extra services to your Kubernetes cluster to enhance the telemetry you can gather, we added two new components:

1. **Grafana SDK Injector**: This new utility has been developed by the Beyla team. The goal of the SDK injector is to simplify the process of injecting the OpenTelemetry SDK into services running on the Kubernetes cluster. This would be used in conjunction with something like Grafana Cloud's instrumentation hub. If you're familiar with that, the SDK injector will make it much easier to extract data from services and applications running in your cluster.

2. **Beyla K8s Cache**: This has been part of the Grafana Beyla project for a little while now. The idea is to cache a lot of the information that Beyla tries to retrieve repeatedly from the API server, reducing the load on the API server and enhancing processing capabilities. This has been working great for our standalone Beyla within the Kubernetes Monitoring Helm Chart. However, if you're using Beyla from inside Grafana Alloy, it didn't have a K8s cache. Now, we have a way to deploy a standalone K8s cache within the telemetry services.

The big feature for 4.2 is **Data Processors**. This is a new concept within the Helm chart. If you've attended these meetings before, you know I've talked about this. The idea behind a data processor is that you generate your telemetry data from features like cluster metrics or pod logs. You send them first to a data processor that processes that telemetry data before it gets sent to the destination. It's kind of a middleware that is agnostic of the telemetry data type.

We added two data processors in the 4.2 release:

- **Kubernetes Enrichment**: This allows you to add a label to telemetry data based on the namespace it comes from. If there's a namespace label, it finds a Kubernetes label on that namespace and adds it as an attribute or label onto the telemetry data. This has been beneficial for users wanting to do cost accounting per namespace or assign team labels based on the namespace.

- **EC2 Enrichment**: Similar to Kubernetes enrichment, if you are running on an EKS cluster with EC2 nodes, you can set tags on those EC2 nodes. We can pull the tags from those nodes and add them as telemetry data labels.

**Host Metrics**: This is essentially our scraper for node exporter, Windows exporter, and similar tools. I made a change to host metrics so that for node exporter, specifically for the Linux host sub-feature, you can skip node exporter altogether and just use the Alloy configuration. Alloy has a built-in copy of node exporter, and if configured correctly, we can use that internal version to gather your host metrics. This means one less daemon set to deploy and one less set of pods to scale.

We also had some great contributions from the community to fix some discovery rules that weren't quite working or were missing on some integrations. I really appreciate the pull requests for that. Additionally, we added a ton of new Alloy collector presets. Presets are a new feature we introduced in the 4.0 release, making it easy to set up snippets of Alloy configuration for common settings.

### 4.3 Release Highlights

We had two patch releases on top of that: 4.3, which came out last week, and 4.3.1, which was released yesterday. Some notable features in these releases include:

- A new flag in many features called **Align Service Name with OTel SemConv**. This is opt-in for now, but the idea is to ensure that we set things like service.name or service.namespace according to the OpenTelemetry semantic conventions. This aligns based on annotations or labels set, and down the line to the deployment name, stateful set name, pod name, and container name. 

- New load balancer options for the service graph metrics. When using the service graph metric feature for the OTLP destination type, the only way we were doing load balancing was through the Kubernetes load balancer, which involved querying the API server for the set of pods for the service graphers. We added many configuration options to tune this, including the ability to do static routing or DNS-based routing.

Thank you for joining today, and I look forward to your questions!

A lot of these changes are in service of instrumentation hub and fleet management-based deployments where you want to push the configuration for Alloy down to this collector, but you need to do some deployment-time things like opening up these ports. The OTLP receiver preset makes it so that those ports get opened up really simply.

There are two new validators that I'm really excited about. If you've used the Helm chart, you know that we try to do a lot of Helm validation of the configuration and of the cluster before you deploy to protect against known bad configurations. One of the validators I added yesterday, in the 4.3 release, looks for Alloy operators that are already on the cluster. We found that if there are two Alloy operators on the cluster that are both cluster-scoped, meaning they're looking for Alloy instances across the whole cluster, not just within their own namespace, they will start to bounce reconciliation for each other. One will reconcile the Alloy instance and start everything up, and then the other one will say, "Hey, things look like they changed. I'm going to reconcile," causing a lot of churn. 

Now, when you do a Helm install, we look for any existing Alloy operators. If there are any, we check to see if they're cluster-scoped or not. If they are, we recommend that you skip your own Alloy operator deployment and use the one that's already there. If they're namespace-scoped, it should be fine because one Alloy operator operates in namespace A, while the Helm chart deployment you're doing now would operate in namespace B, and they'll behave just fine. This should catch some issues we've seen in the field before where you want to deploy two copies of the Helm chart, maybe for multi-tenancy or similar situations.

Another validator checks the stability levels for Alloy components. Some components are in public preview, while others are experimental. Previously, we checked feature by feature, but we've added a new, much more generic way to check all component levels and all components in your Alloy config. This will recommend that you set the stability level at the right level. The benefit is that it will also catch things added into the extra config. If you put in something that's an experimental-level component into extra config for a collector, but the stability level doesn't match, we will check that at deployment time. This means much less hunting down crashed Alloy instances or looking at pod logs; we'll try to catch these things early on.

Additionally, there are even more dependency updates and bug fixes. That's all that's been happening in the 4.3 release.

You set your feature to send to the router, and based on a label set on the telemetry data coming through—maybe the namespace name or a special tenant ID label—it will send to different other destinations. 

In a multi-tenancy situation, if you have five different metrics backends for different tenants, you can use the router as one destination, and it will automatically distribute the telemetry data to the right destination based on matching labels.
