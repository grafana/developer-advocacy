Key features highlighted included the ability to deploy Alloy collectors on Windows nodes, the introduction of a router destination for complex telemetry data routing, and new receiver features for Prometheus metrics and Loki logs in version 4.5. Hi everybody. Welcome to the August edition of the Kubernetes Monitoring Helm Chart Office Hours. My name is Pete. I am one of the engineers behind the Kubernetes Monitoring Helm Chart, and we have a bunch of things that we're going to talk about today.

There are actually two feature releases, 4.4 and 4.5, that we released this month. Like last month, we released two feature releases, and I think this kind of enhanced velocity can be attributed to two different things. First off, we're trying to stick more towards a proper sub-version. So anything that really does feel like new content or new functionality goes into at least a dot release. Anything that goes into a double dot or a patch release is really just bug fixes. Secondly, there's just been a lot of really good new features that we wanted to highlight and get out into the public as fast as possible.

### Kubernetes Monitoring Helm Chart 4.4

This was released a handful of weeks ago, and the major feature that came with this one is the ability to deploy Alloy collectors and Alloy instances onto Windows nodes. Kubernetes nodes running the Windows operating system can now utilize Alloy, which has been built to run on Linux, Windows, and Mac OS. For Kubernetes, it has only been available for Linux for a long time. We figured out the special deployment pattern needed to make it work on Windows nodes, and so 4.4 makes that really easy. 

There's a new Windows preset that you can add to your Alloy collector definition, which will configure it to run on Windows nodes. 

**Advantages of Running an Alloy Instance on Windows Nodes:**
- **Windows Event Logs:** Just like the node logs feature where you get journal D logs from a Linux node, this will get the event logs off of the Windows operating system, which can be system-level logs or application logs.
- **Host Metrics Feature:** Just like we did with node exporter and Linux node metrics, the host metrics for Windows nodes can now come directly from Alloy rather than just using the standalone Windows exporter project. This reduces another daemon set that you might want to deploy.
- **Smaller Footprint:** For the case monitoring Helm target deployment.

There's another new feature, a new destination type called **Router**. This one's really exciting. It was created by a different Grafanista who has had this idea for a long time and finally got it developed and released. 

I've got a slide that will go into more depth about what you can do with the router destination, but essentially, it allows for more complex delivery of telemetry data based on some of the attributes or labels on that telemetry data. 

**Support for Namespace Regexes:** A lot of features have the ability to specify a namespace list. For example, in one of the pod logs features, you can specify which namespaces you want to get the pods from to get the logs. Until 4.4, those had to be named namespaces. Now, it supports regexes. 

Why did it take so long to do this? The way we filter the pods based on those namespace lists changes if you're using a regex or if you're using straight lists of namespaces. We are looking at the content of that list and determining if we can be more efficient because they're specific namespaces, or if it's a regex, then we have to use more of a filtering option.

We've added more validators for detecting port conflicts, so hopefully, you will have a better experience when deploying the Helm chart. As always, there are lots of dependency updates and bug fixes.

### Router Destination Overview

This is a quick diagram that I created for describing what the router destination does. Some people are approaching the router destination with the idea of doing something like multi-tenancy. There are plenty of different ways to use this to add complex routing decisions. 

The idea here is to pretend you've got three Prometheus-type destinations defined: metrics alpha, metrics beta, and metrics default. Then you have this metric router, which is declaring, "I'm part of the Prometheus ecosystem, so I'm expecting Prometheus metrics." You always have to specify a default, but the interesting part is the routes block. 

It says to look at all the metrics coming through, and if the namespace label matches tenant A, then send it to metrics alpha. If the namespace label matches tenant B, then send it to metrics beta. Otherwise, the fall-through will go to metrics default. 

You can start to see how you can set up complex routing topologies based on the type of data coming into the router destination. It doesn't have to be only with metrics; you can set up routers to do things with logs, traces, profiles, and any of the OpenTelemetry data, matching on the resource attributes.

### Kubernetes Monitoring Helm Chart 4.5

Now, KSM Monitoring Helm Chart 4.5 was just released this week, and we've got some other cool features that came with that. 

A new feature, kind of a pair of features, includes the Prometheus metrics receiver and the Loki logs receiver. Before this, we had two other receiver-type features: a profiles receiver where things could generate profiles and then be delivered to Alloy for labeling and post-processing, and the application observability feature, which is essentially an OpenTelemetry receiver. 

You can receive OpenTelemetry signals, metrics, logs, and traces, perform some standard processing inside of the Alloy Collector, and then deliver them to any of the databases that support those telemetry types. However, we hadn't had the ability to add a logs receiver or a metrics receiver using the Prometheus or Loki ecosystems.

Both the profiling feature and the integrations features now have the ability to set your collector where you're setting this configuration on the sub-level feature. In the profiling feature, there's Java profiling, eBPF profiling, or pprof profiling. They do different things, and there may be reasons why you want to put the configuration for one onto one collector and the configuration for another on a different one. 

Now you can mix and match; it doesn't all have to be on a single collector. The same applies to the integrations; each integration instance can be set onto a different collector if needed. This can be really great if you know that one integration is paired directly with your MySQL database, and you want that integration instance to go on that one, while another one goes on a broader deployment or daemon set.

A minor update: the destinations all set the cluster label. When you are defining the Kubernetes Monitoring Helm Chart values file, you set the cluster name. It's the destination components that...

actually set that name onto the telemetry data before it gets delivered. I discovered there's a little bit of a mix and match on how that name label gets set. Some of them will overwrite if the cluster label already exists, while others will not overwrite if the cluster already exists. In version 4.5, I've made it so that you can either force them to overwrite or force them to never overwrite. Right now, they match their default behavior. In version 5.0, we'll probably change that so that they will never overwrite. This means that if the cluster label is already set, it will maintain what it's set to.

I promised to show a diagram about what you can do now that we have the metrics and logs receiver features. This spaghetti diagram illustrates the concept of the gateway pattern. If you have Kubernetes clusters that do not have the ability to egress traffic out to Grafana Cloud or wherever your telemetry databases are running, you need to run them through some sort of intermediate gateway. 

For example, if you have a leaf cluster where your applications are running, you can deploy the Kubernetes Monitoring Helm Chart as usual to get all of the normal telemetry data, such as cluster metrics, application metrics, and logs. Instead of trying to send those to Grafana Cloud or any offsite database storage, where they cannot egress, you can send them to a different Kubernetes Monitoring Helm Chart deployment, a gateway deployment. The only features that would be enabled in this deployment are the new receiver features. 

The metrics and logs receivers are the new features that we just added in version 4.5. The profiles receiver has been there for a while. The OTLP receiver is effectively the application observability feature. If you enable those four features, the Kubernetes Monitoring Helm Chart deployment in the middle is really just waiting and listening for telemetry data to be sent to it. You can do a little processing, such as log redaction, relabeling, and filtering. This gateway cluster then sends the telemetry data off to the databases for storage. 

This is one of the exciting ideas you can implement with the gateway pattern and the new receivers feature. This also shows why I wanted to get the ability to overwrite or force to never overwrite the cluster label. I want to ensure that the gateway cluster never changes the cluster labels when they come from those leaf clusters, so that you have traceability of where that data came from. 

So, those are the updates for the 4.4 and 4.5 versions. Now, let's talk a little bit about what we have planned for version 4.6 and the next major version 5.0. These are all subject to change; this is kind of penciled in for now. 

For version 4.6, we are considering adding more security hardening. Some work has been done to tighten up the node exporter and some of the permissions that it requests, as well as for Alloy. Running Alloy, it tries to maintain a balanced security footprint where it's not asking for too much, but at the same time, it needs to be broad enough because it doesn't make assumptions about what sort of configuration you are placing onto that Alloy collector. We will look into ways to inform that balance more intelligently based on the configuration that you're deploying onto Alloy.

Some people have been asking for the configuration validation pre-install hook to be returned. This was a feature way back in the 1.0 timeframe where, when you deployed, the first thing we would do is perform some basic checks of the Alloy configuration and then fast fail if something wasn't right, such as a syntax error. I removed it in 2.0 because I was concerned that it was taking too long for the Helm chart to deploy. However, some people really liked that validation, so we will add that back in as an optional run, probably having it disabled for the time being. But it will be there if you want to have some extra checks and assurances that things will run correctly.

In version 5.0, we have a couple of really cool things planned. I've talked about this a little bit, but I'll highlight it here again. The next thing we are considering for version 5.0 is the ability to deploy OpenTelemetry-style collectors. This means that in your collectors field of the values file, you can specify whether this is an Alloy collector or an OpenTelemetry collector. We do not plan to have full feature parity when it comes to the configuration features, such as cluster metrics and cluster events. We are not planning on having that level of parity all in version 5.0, but maybe feature by feature, we will see what makes sense to bring over as far as what's supported on an OpenTelemetry Collector versus on an Alloy Collector.

The Kepler Helm chart is part of the energy metrics feature that we have. Kepler has moved where their Helm chart is pulled from, and we need to be able to move that too. Unfortunately, there's not really a nice clean way to do that in a minor release, so we will save that for the next major release.

The Alloy Operator namespace will be a larger change in how the Alloy Operator gets deployed. Right now, it operates over the entire cluster. If you deploy an Alloy object in any namespace, this Alloy Operator will be able to turn that into a running Alloy instance. The problem is that this causes issues if you deploy two copies of the KSM Monitoring Helm Chart, as the two Alloy Operators might start fighting over those Alloy instances. By default, we will make them namespaced to the location where you're deploying the Helm chart. This makes it simpler to deploy multiple instances.

Similar to the security hardening with Alloy, we will look into the minimization of RBAC. When deploying these Alloy instances, if you can understand what the configuration is doing, you can make decisions about what sort of permissions within the cluster you need to have. We can reduce the RBAC permissions for that running Alloy instance to only what it needs to operate. This would be really helpful for many cluster operators. It also provides more insight when deploying new configurations down to Alloy, as it will indicate if adjustments to the cluster roles or the roles and role bindings are needed due to new features requiring extra permissions. This gives you more informed decisions about the ramifications of running different configurations.

As I said, all of this is subject to change, but these are what we have penciled in for the next feature and major releases. Now is the time for questions and answers.
