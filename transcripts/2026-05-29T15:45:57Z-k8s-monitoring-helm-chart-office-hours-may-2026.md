## Summary

The show is titled "k8s-monitoring-helm Chart Office Hours" and was held on May 29, 2026. The speaker, Pete Wall, the primary engineer for the Kubernetes monitoring Helm chart, discussed the release of version 4.1 and upcoming features in version 4.2 of the Kubernetes monitoring Helm chart. Key features of version 4.1 included the Kubernetes manifest feature, which captures YAML manifests for better observability, and various enhancements to Alloy components, such as the ability to replace component content and set cluster names from external options. The upcoming version 4.2 is expected to introduce processor features for telemetry data enrichment and potentially integrate cert-manager for improved application observability.

Hello everybody and welcome to the May edition of the Kubernetes Monitoring Helm Chart Office Hours. I'm Pete Wall, the primary engineer for the Kubernetes Monitoring Helm Chart, and we can get started.

Today on the agenda, we're going to talk about the 4.1 release, the latest feature release of the Kubernetes Monitoring Helm Chart version 4. We'll discuss what's planned for 4.2, the next feature release, and one more deprecation notice for V1 and V2. We'll leave it open for questions and answers.

**Kubernetes Monitoring Helm Chart 4.1**

We released this on May the 4th, on Star Wars Day, and this was a cool feature release on top of the big 4.0 release. A couple of notable new features that came with 4.1 include:

- **Kubernetes Manifest Feature**: This feature allows you to enable it and capture the YAML manifests of the objects within your Kubernetes cluster that you want, such as pods, deployments, and services. The service will talk to the API server, get those YAML manifests on startup, and then when things change. We capture those as log data, which can be pushed up to a Loki log store. The reason for this is that it adds the actual manifest that was running at a certain time into your observability platform. You can perform diff analysis, and if your AI agents, like Grafana Assistant, are connected to this, you can provide them with extra information about issues you're seeing, along with the actual manifest that was running at the time. I've marked it as experimental for now, and there are some things that I'll probably change in the future, but if you want to start playing around with this, definitely give it a shot.

- **Alloy Component Content Replacement**: This is something that people have been asking for a long time. Essentially, the KSM Monitoring Helm Chart generates a large config map for each Alloy instance, and Alloy configs are built into what are called components. You'll see something like the component name or component type, followed by the definition of that component in curly braces. What we've added in 4.1 is the ability to choose a component, either one inside a feature or one at the top level, and provide replacement content for that. This is useful if there is something you want to set in a component that we don't support or offer a switch for, and you don't want to wait for an upcoming release. However, it wouldn't necessarily be a long-term solution, as updates to that component may not apply to your changes.

- **Cluster Name Setting**: The cluster name can now be set from an external option, which has been a long-requested feature. In the KSM Monitoring Helm Chart, one of the required fields is `cluster.name`, which sets the cluster label in a lot of the telemetry data. You can now set that from an external config map or an environment variable.

- **Global Namespace Override**: This feature allows you to deploy the Helm chart itself into one namespace while changing where the actual generated artifacts get deployed, such as Alloy instances and the Alloy operator. This also cascades down to components like Node Exporter and Kube State Metrics.

- **More Presets for Alloy Collectors**: In 4.0, we generalized the collector definition, allowing you to define how your Alloy instances look. We introduced presets, where you can give a one-word preset that sets many Alloy features behind the scenes. We've added more presets that set the resource requests and limits for the Alloy containers, such as small, medium, large, and extra-large.

- **Cluster Events Feature**: This feature added support for Alloy clustering. Previously, gathering Kubernetes cluster events was not clusterable, leading to duplicate log data if deployed on more than one replica. Now, you can deploy the cluster events feature on any collector, and as long as Alloy clustering is enabled, it will avoid duplication of event data. This means you likely don't need Alloy singleton in your collector fleet anymore.

- **Prometheus Destination Support for Prometheus Rules**: We added support for Prometheus rules, allowing you to detect those rules and apply them to your Prometheus destination. This means you can define recording and alerting rules and push them to your compatible destinations. It's an early feature, and I'm glad we got this one out there. I'd be really happy to hear if you're using it and what you think.

Since the 4.1 release, we also released a few patch releases. Notable changes in the patch releases include:

- **Cost Metrics Feature**: The cost metrics feature no longer defines the static API token. Previously, we had a static API key in cost from OpenCost, which was necessary for deployments in GKE. We found a way to disable the requirement for that API key while maintaining compatibility for every platform we typically deploy onto. You won't see that anymore, which solves a major headache for me.

Secret scanners will be able to say, "No, no, no, this one's fine." So, that's nice to see. Hopefully, you all enjoy that, too. 

There are general improvements, including better native histogram support for metric scraping. There are options to scrape classic histograms, native histograms, and convert classic to native. All of that has been added, so if you're using one or the other and need support for that, it should be better available to you.

An improvement for the Loki destination is that you can now use write-ahead logs for the Loki destination types. For the OTLP destination, if you're using tail sampling, there is now a drop policy. If you've been looking for the drop policy, it should be there, too. 

With our patch releases, we update our dependencies, including things like node exporter, kube state metrics, OpenCost, and more. There are also lots of other smaller bug fixes. I plan to release version 4.1.4 probably later today, which will include some more bug fixes, so look for that.

Now, let's talk about what's coming in version 4.2. This will be the next feature release, and we have a few features planned. Likely, this will expand as we get more information about what people are looking for. 

One of the features is the processors feature. This is something I wanted to get into version 4 and then into 4.1, but it's taking a little longer to reach a point where I really love it and feel good about it. The idea behind the processors is to define a component in the Helm chart so that all telemetry data captured somewhere flows through these components to do some work before going off to the destinations. 

I'm particularly excited about the Kubernetes enrichment. If you have namespaces with labels and want to add that label to all of your telemetry data or certain telemetry data—like all of your metrics and logs—this will help. In the past, we had a metrics enrichment feature inside the Prometheus destination that did something similar, but rather than defining it destination by destination, I want to have one processor where you can feed all of your data through, and then it gets delivered to the assigned destination.

Another feature is EC2 enrichment, which has been requested by a user. This would add labels to your telemetry data based on EC2 tags. If you've tagged your EC2 nodes with certain tags, we can detect that and add it as telemetry data. As this feature matures, I expect there will be other processors involved as well, such as a GCP one.

We're also considering bundling in cert-manager. We'll do this intelligently, looking at your cluster to avoid conflicts. Why would we want cert-manager? There are improvements coming to Grafana Vela that allow for much more intelligent injection of Java instrumentation. To support this, they will be adding a mutating webhook, and cert-manager will enable this enhanced behavior of Grafana Vela. We'll be working closely with that team to ensure everything is done well, which will allow for some interesting auto-injection and application observability features.

As stretch goals for 4.2, I'm considering including the OpenTelemetry operator, which has some auto-injection options that are really exciting. Another long-term stretch goal is the possibility of deploying OpenTelemetry collectors as well as Alloy collectors, now that collectors in version 4.0 can be defined in various ways. I have ideas on how to implement this, but no guarantees it will make it into 4.2.

Now, a deprecation notice: versions 1 and 2 will be deprecated on June 1st, which is just a few days away. This means I will no longer be creating patch releases, and we will remove version 1 from the main branch of the Kates Marine Home Chart Git repository. If you are on version one or two, please start thinking about how to migrate to either version three or version four. I suggest version four, as it receives new features and faster releases. Version three will continue to receive dependency updates and bug fixes, but it will take longer.
