## Summary

The show is titled "k8s-monitoring-helm Chart Office Hours" and was held on October 30, 2026. The speaker, Pete Wall, discussed the upcoming release of version 4.6 of the Kubernetes monitoring Helm chart, highlighting key features such as security enhancements for node exporter, new cache TTL options, and improved Prometheus operator support. He also previewed future updates, including integration for MS SQL databases and enhancements to the Alloy operator. Key takeaways include the focus on security hardening, improved configuration management through Grafana Fleet Management, and ongoing efforts to streamline the user experience.

For example, for the node exporter, we've turned allow privilege escalation off. There are a lot of settings on services like node exporter that we just don't need, and it makes it faster for people who are running clusters that they want to tighten down the security if we handle some of those things by default. So, node exporter is starting to get tightened up.

We also removed a lot of the default Linux capabilities out of Alloy. We've tested all these things, and it seems that there's no change in functionality, so we've done that. Another change is that there's a cache TTL option inside of the Prometheus relabel components. That's now available; you can set that either globally or into the individual features.

There’s a change to the Prometheus operator object support. Now, there's a namespace field where you can either select Prometheus operator objects, such as service monitors or pod monitors, and select them by namespace or exclude them by namespace. If you have a namespace where you just say, "Don't capture anything in these namespaces," you can set the exclude namespace. In 4.6, those fields now support regex. So, you can do something like an include namespace on `team.*`, and it'll capture any Prometheus operator object inside of team A, team B, team C. Prior to this, you had to explicitly name each namespace that you wanted to use.

The Prometheus destination got an enhancement where, now, this is not enabled by default, but it's an option. If you're using metric re-labeling rules, the previous approach up until 4.5 would unfortunately set those re-labeling rules after the destination components applied its write-ahead log (WAL). What that meant is if you set a write-ahead log and were persisting this to disk, and then you used these metric re-labeling rules to drop a lot of metrics, those metrics would still be written to disk before those re-labeling rules happened. The result of that is some metrics would be stored that didn't need to be stored, using up more storage than necessary. So, there's now an option to apply these rules before the write-ahead log happens. Internally, we use a new re-label component to apply these rules before the destination component, allowing you to drop a lot of metrics before applying them to the write-ahead log, saving space.

A new change to the OTLP destination adds resolver options into tail sampling. Prior to this, the service graph metrics feature inside of OTLP also had an enhancement to add resolver options. Resolver options determine how to handle load balancing when targeting the new Alloy that gets created for the service graphs or tail sampling. Previously, it would always work using Kubernetes, but now you can make it by DNS or by static resolution. This should speed things up and improve compatibility across different platforms.

As always, with all of our updates, we try to keep to the latest of all of our service dependencies and address various bug fixes. That's everything coming in on 4.6. Again, I'm looking at the tests right now, and we're still running them. Whenever we release, we run a full suite of what we call platform tests, ensuring compatibility with cloud providers, which always takes a little bit longer to create those clusters.

Now, for a preview of what we have coming up, we have a lighter docket for the future features we want to include. For 4.7, in the next minor version update, we're still looking into doing the configuration validation option. Additionally, we plan to add a new integration for MS SQL databases. Support has been added for that in Grafana Cloud database observability, and I want to make it easy to install an integration if you're using the Kubernetes Monitoring Helm chart as well. It should be a fairly simple feature since it will be very similar to the MySQL integration.

In the next major release, we're starting to narrow down exactly what we want to include. Some of these things are items we've kept from previous months. We're still looking into OpenTelemetry collectors as an alternative to the regular Alloy collectors. The Kepler Helm chart has moved its Helm chart location, and unfortunately, in the world of Helm, you can't just point from one to the other and have it upgrade; it behaves as if it's a new chart.
