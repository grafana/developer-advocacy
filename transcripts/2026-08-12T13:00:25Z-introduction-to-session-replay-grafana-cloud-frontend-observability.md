Hi, I'm Bacola, senior developer advocate at Grafana. In this video, I'll show you how to use session replay in Grafana Cloud Frontend Observability to visually replay user sessions and debug frontend issues. 

One of the most frustrating problems as an engineer is when a user reports a bug, you can't reproduce it, and your logs don't tell you enough. Session replay lets you see what a user saw and did during their time in your application, so you can catch hard-to-reproduce bugs without relying on guesswork. This makes it much faster to investigate and fix issues that would otherwise take hours to resolve using logs and error messages alone.

Session replay is one of the newest features in Grafana Digital Experience Monitoring. It lives inside Grafana Cloud Frontend Observability and works alongside the real user monitoring data that the Faro web SDK is already collecting. This means engineering teams can go from a symptom to a root cause without bouncing between tools or teams.

Behind the scenes, session replay works by recording browser interactions, such as clicks, scrolls, and text inputs, and reconstructing them as a playable session inside Grafana Cloud Frontend Observability. It's important to understand that session replay isn't recording a video of the user's screen. Instead, it captures a structured representation of the page and the user's interaction with it, including DOM snapshots, DOM mutations, user interactions, and lifecycle events. 

Session replay doesn't capture network requests, audio and video content, or console logs. That said, signals like console logs, web vitals, and network requests are still captured by the other instrumentation libraries of the Faro web SDK, so you are not losing that visibility. 

Masking is applied on the client side before any recording data is sent to Grafana Cloud. By default, all input text and all text content on the page are masked. Passwords are also masked by default for privacy, but they can be captured if you explicitly configure it. These recordings are correlated with your existing Faro telemetry, so you can jump directly from a frontend error or a log into a corresponding replay.

The key benefits of session replay include:

- **Faster debugging**: You can see exactly what a user did without asking them to walk you through it again.
- **User journey visibility**: Spot where people are getting stuck or hitting poor experiences.
- **Privacy by default**: Inputs and text are masked before anything leaves the browser, making it safe to run in production.

Let's now walk through the four steps required to set up your first session replay recording. 

**Step 1: Install the replay instrumentation package.**  
Open your terminal and run the install command for the Faro replay instrumentation package.

**Step 2: Import and initialize session replay in your application.**  
Import the replay instrumentation class alongside your existing Faro imports. Then pass a new replay instrumentation object into the instrumentation array where you initialize Faro. That's the minimum configuration to get started. Session replay will now record user sessions and forward them to your Grafana Cloud collector endpoint.

**Step 3: Configure sampling.**  
Let's move to step three by adding sampling to our configuration. Session replay uses two independent layers of sampling. The first is Faro session sampling, which controls which sessions Faro collects telemetry for, like logs, errors, and traces. The second is session replay subsampling, which controls what fraction of these sessions also get a recording. For example, if you want to collect telemetry for all sessions but only record replays for 10% of them, you would configure it like this. This means your effective replay coverage is 10% of all sessions, which helps you control data volume and costs while still capturing a representative sample. But for the purpose of this video, we'll set both sampling rates to 100%. This means every session will have telemetry collected and every session will be recorded.

**Step 4: Configure privacy and masking.**  
Let's move on to our final step by configuring masking and privacy. The default masking configuration is privacy-first, but you can tweak the masking options to fit your needs. All input values and text content are masked by default client-side before data leaves the browser. You can make masking more effective by using the mask all inputs and mask input options property. For example, to unmask most inputs while keeping passwords, email addresses, telephone numbers, and text area content masked, you would configure it like this. Once your configuration is saved and your application is running, session replay is active and recording.

Our application has been instrumented and running for a few minutes, so let's now review the results. On the Quick Pizza website, we'll click a few buttons and experiment with the app the same way a real user would. All of that information is being recorded and sent to Frontend Observability, which is where you'll find session replay.

Now we'll head into the Frontend Observability dashboard and open the sessions tab. From the sessions tab, you can browse and filter recorded sessions by date, user, or application. You can jump directly from an error, log, or trace into the corresponding replay. You can use the replay to reproduce and investigate frontend issues.

To view session recordings, you have two options. You can open a session directly from the session detail page. However, we recommend clicking the green button to open the player in a new tab. This lets you watch your recording side-by-side with the full user journey, which always stays synchronized with the player state. 

When you select a session, you can view the recording either inline alongside the user journey data or in a full-screen view. The replay player gives you full control over playback. You can play, pause, and skip 10 seconds forwards or backwards. You can also adjust the replay speed with options from 0.25x all the way to 16x, so you can quickly scan longer sessions. The skip inactivity toggle lets you jump past parts of the recording where there's no user activity, which helps you focus on what matters. The share button lets you copy a link to a specific moment in the replay, so you can send it directly to the teams when you're debugging an issue.

One of the most powerful things about session replay is that it's correlated with your existing Faro telemetry. If you see a frontend error in your dashboard, you can jump directly into that replay for the session and see exactly what the user was doing when the error occurred. That's real user visibility and fast resolution in the same workflow.

There you have it. You now know how to instrument session replay with the Faro web SDK, configure sampling and masking, and use the replay player in Frontend Observability to investigate frontend issues.
